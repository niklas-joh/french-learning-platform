# Task 3.1.C.7: Implement Async Weakness Analysis Worker

## **Task Information**
- **Parent Task**: 3.1.C - AI Assessment & Grading Engine
- **Task ID**: 3.1.C.7
- **Estimated Time**: 1.0 hour
- **Priority**: 🟢 High
- **Dependencies**: 3.1.C.1 (DB Schema), 3.1.C.5 (Assessment Repository)

## **Objective**
To create a background worker that asynchronously analyzes a user's recent assessment history to identify strengths, weaknesses, and learning patterns. This moves heavy analytical processing off the synchronous API request path, ensuring the `/api/v1/assessment/analysis` endpoint remains fast and responsive.

## **Success Criteria**
- [ ] A new `WeaknessAnalysisService` is created to contain the analysis logic.
- [ ] The service fetches recent assessment data for a user from the `AssessmentRepository`.
- [ ] The service performs aggregations to identify patterns (e.g., most common incorrect categories).
- [ ] The service uses an AI call (via `PromptTemplateEngine`) to generate a qualitative summary and recommendations.
- [ ] The final analysis report is saved to the `user_weakness_analyses` table.
- [ ] A mechanism to trigger this worker is established (e.g., a job queue or a scheduled task).

## **Implementation Details**

### **1. Architectural Shift: Asynchronous Processing**

As identified in the critique, performing this analysis in real-time is not scalable. The architecture will be as follows:

1.  **Trigger**: An event is fired when a user completes a significant number of exercises (e.g., 5) or on a time-based schedule (e.g., once a week).
2.  **Job Queue**: This event adds a `analyze-weakness` job to a queue (the same queue system from Task 3.1.B).
3.  **Worker**: A dedicated worker process picks up the job.
4.  **Service**: The worker calls the `WeaknessAnalysisService` to perform the analysis.
5.  **Store**: The service saves the result to the `user_weakness_analyses` table.
6.  **API**: The `GET /api/v1/assessment/analysis` endpoint now performs a simple, fast read from this table.

### **2. `WeaknessAnalysisService`**

This new service will encapsulate the entire analysis process.

```typescript
// server/src/services/weaknessAnalysisService.ts

import { Knex } from 'knex';
import { OpenAI } from 'openai';
import { AssessmentRepository } from '../repositories/assessmentRepository';
import { PromptTemplateEngine } from './promptTemplateEngine';
import { UserAssessment } from '../types/Assessment'; // Assuming this type exists

export class WeaknessAnalysisService {
  constructor(
    private db: Knex,
    private openai: OpenAI,
    private assessmentRepo: AssessmentRepository,
    private promptEngine: PromptTemplateEngine
  ) {}

  async performAnalysis(userId: number, timeframeDays: number = 30): Promise<void> {
    // 1. Fetch raw assessment data from the repository
    const recentAssessments = await this.assessmentRepo.getAssessmentsForUser(userId, timeframeDays);

    if (recentAssessments.length < 10) {
      // Not enough data for a meaningful analysis
      return;
    }

    // 2. Perform quantitative analysis (pattern recognition)
    const mistakePatterns = this.analyzeMistakePatterns(recentAssessments);
    const confidence = this.calculateAnalysisConfidence(recentAssessments.length);

    // 3. Use AI for qualitative analysis and recommendations
    const prompt = this.promptEngine.generateWeaknessAnalysisPrompt({
      mistakePatterns,
      timeframe: timeframeDays,
    });
    
    const response = await this.openai.chat.completions.create({
      model: 'gpt-4',
      messages: [{ role: 'user', content: prompt }],
    });

    const analysisContent = response.choices[0]?.message?.content;
    // TODO: Parse and validate the AI response using a Zod schema

    // 4. Save the final report to the database
    await this.assessmentRepo.saveWeaknessAnalysis(userId, {
      analyzedAt: new Date(),
      timeframeDays,
      confidenceLevel: confidence,
      // ...data from parsed AI response
    });
  }

  private analyzeMistakePatterns(assessments: UserAssessment[]): any {
    const mistakes = assessments.filter(a => !a.isCorrect);
    const pattern = mistakes.reduce((acc, mistake) => {
      const category = mistake.assessmentType; // Or a more specific category if available
      acc[category] = (acc[category] || 0) + 1;
      return acc;
    }, {});
    // Return sorted patterns, etc.
    return pattern;
  }

  private calculateAnalysisConfidence(dataPoints: number): 'low' | 'medium' | 'high' {
    if (dataPoints >= 50) return 'high';
    if (dataPoints >= 20) return 'medium';
    return 'low';
  }
}
```

### **3. Worker Implementation**

The worker will listen for jobs and execute the service.

```typescript
// server/src/workers/analysisWorker.ts

import { Job } from 'bullmq';
import { WeaknessAnalysisService } from '../services/weaknessAnalysisService';
import { orchestrator } from '../server'; // Assuming singleton

async function processWeaknessAnalysisJob(job: Job<{ userId: number }>) {
  const { userId } = job.data;
  const analysisService = orchestrator.getWeaknessAnalysisService(); // Orchestrator provides the service

  try {
    await analysisService.performAnalysis(userId);
  } catch (error) {
    console.error(`Failed to analyze weaknesses for user ${userId}`, error);
    throw error; // Allow BullMQ to handle the retry logic
  }
}

// This worker would be initialized and started with the main application
```

## **Review Points & Solutions**

-   **🔍 Review Point: Performance**
    -   **Concern**: Real-time analysis of a user's history is too slow for an API endpoint.
    -   **Solution**: This entire task is the solution. By moving the analysis to an asynchronous background worker, the user-facing API endpoint becomes a simple and fast database read, ensuring a good user experience.
-   **🔍 Review Point: Triggering Mechanism**
    -   **Concern**: When should an analysis be run?
    -   **Solution**: The system can be configured with multiple triggers. A good starting point is to add a job to the queue after a user completes a certain number of exercises (e.g., every 5th completion). A weekly scheduled job could also run to catch all active users. This provides a balance between timely feedback and efficient processing.
-   **🔍 Review Point: Data Requirements**
    -   **Concern**: What if there isn't enough data for a good analysis?
    -   **Solution**: The `performAnalysis` method includes a guard clause that exits if a minimum threshold of data points (e.g., 10 assessments) is not met. This prevents wasting resources on meaningless analyses and avoids providing the user with low-quality, unhelpful feedback. The confidence level also reflects the amount of data available.
